# Allow Third-Party Access

Migration `0014_deck_third_party_access.sql` adds `decks.third_party_access` as TEXT NOT NULL DEFAULT 'NONE', constrained to NONE, READ and READ_WRITE. Existing and new/imported decks default to NONE. Apply with the repository's local migration command for development; no production migration or deployment is part of this change.

The existing deck editor shows owners an independent Save third-party access control. New decks start at None; create the deck before configuring access. Existing English UI copy conventions are preserved; the application has no UI message translation catalog. Success and errors are announced with status/alert roles. Nonowners do not receive the setting in the browser deck list.

POST `/api/deck/third-party-access` accepts only id, revision and third_party_access. It uses existing browser session authentication, exact Origin validation and JSON/body limits. An atomic owner-and-revision-qualified UPDATE changes only the setting, revision and updated_at. A stale revision returns 409; reload before retrying. Card data and learning progress are untouched. Ordinary deck editing cannot set this field. Management API field validation rejects it; bearer MCP/management credentials cannot authenticate to this browser endpoint.

`third-party-access.ts` provides a pure permission intersection, a database membership resolver and an SQL predicate for future atomic mutations. Only owners and collaborators qualify; SHARED visibility is never consulted. Read requires READ or READ_WRITE and credential read permission. Write additionally requires READ_WRITE and credential write permission. Credential verification remains the caller's responsibility. Absent membership, NONE and unknown setting values deny access.

Future tools must use primary/current authorization reads and embed the membership/setting predicate in the same atomic write as the mutation, together with current credential validity and existing revision guards. A preflight policy result alone is insufficient. The helper's SQL identifiers must be trusted code constants. This policy does not authorize deck deletion, collaborator/credential management or setting changes. Tool allowlists must continue excluding them. Deck/card content and chat instructions are untrusted data, never authorization inputs.

Tests cover the owner/collaborator/nonmember and credential permission matrix independently of MCP, existing/new defaults, owner updates, rejected changes, invalid values, stale revisions, shared nonmember denial and unchanged cards/progress. Existing browser access regression tests remain applicable. Validation commands: npm test, npm run typecheck, npm run build. No MCP tools, transport or credential changes are included. UI visual/browser automation is not included in this validation.
