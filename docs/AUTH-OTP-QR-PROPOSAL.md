# Supabase Auth, Google, Email OTP and QR proposal

Status: proposed implementation design, 2026-11-22. Supersedes the custom OTP proposal. Approved stack: Supabase Auth for credentials/identity, Cloudflare Workers and D1 for application data and authorization. MCP, Apple, passwords and a custom OAuth server are excluded. [Inventory](AUTH-INVENTORY.md) describes verified current behavior; [plan](AUTH-OTP-QR-IMPLEMENTATION-PLAN.md) defines execution gates. No services have been configured.

## Recommended minimum

Use a small Workers backend-for-frontend: server-side Supabase Google PKCE and Email OTP flows establish the existing opaque Flashcards cookie session. Use that same application session mechanism for direct and QR login. Supabase verifies the new Google/Email OTP methods; the existing shared-code credential verifier remains operational during Phases 1-4. Do not build a second OTP system or expose Supabase access/refresh tokens to TV JavaScript. Keep all application data and authorization in D1.

A QR-approved TV receives a local delegated Flashcards session, not a new Supabase session. The reviewed Supabase flows do not supply a native general-purpose device authorization grant that can mint a separate TV refresh token from phone consent. Do not clone the phone refresh token, use admin generate-link impersonation or mint Supabase JWTs. Reusing local sessions is the narrow technical reason for a local application-session layer. All methods converge on the same internal user and authorization rules; the temporary legacy credential path remains explicitly supported.

Approved policy: preserve fixed **30-day application sessions** for legacy, Google, Email OTP and QR, with the same HttpOnly/Secure/SameSite=Lax cookie format, no sliding renewal and no Supabase refresh-token persistence. Each successful login rotates the current cookie as legacy login already does. A QR-approved device receives its own full 30-day session from completion; it does not inherit the phone's remaining lifetime. Reauthentication uses an approved login method. Existing sessions survive the additive rollout and do not require a Supabase mapping to remain valid.

Explicit logout deletes the current session row and clears its cookie. Add logout-all to delete that user's application sessions and invalidate pending/approved grants in one transactional batch. Protected requests must read authoritative D1 session state without positive-auth caches; the next authorization check after revocation commits fails immediately. This cannot undo a request already authorized/in flight. Concurrent fresh login after revocation is a new session, not a bypass of revocation; account suspension is distinct. QR redemption rechecks the approving session in its batch: logout-first blocks redemption; redemption-first creates an independent TV session which logout-all also removes. A phone-only logout does not revoke an already issued TV session.

Supabase sign-out/deletion/ban/key rotation does not automatically revoke exchanged Flashcards cookies. Incident handling explicitly revokes D1 sessions/device grants and, separately, Supabase sessions/API tokens where appropriate. The still-enabled shared code can authenticate again, including to mapped usernames: Supabase-only bans or logout are not an account lockout. Legacy passwordless security is therefore bounded by the shared-code mechanism until separately approved retirement. Keep its current rate limit, Origin/body checks and authorization. Do not disable legacy for mapped accounts in Phases 1-4 or silently reinterpret revocation as disabling future login.

Supabase outages affect new Google/OTP authentication; legacy login and existing D1 sessions continue. No token vault or alternate authorization layer is introduced.

### Alternative evaluated

Use Supabase access/refresh sessions directly for phones/desktops and local cookies only for QR. This gives native refresh there but creates two browser validation/logout paths and does not solve native TV issuance. A server token vault could hide refresh tokens but adds encryption, concurrent refresh locking and recovery logic. For two users these are unnecessary. Recommend one local cookie path for all devices and a single Supabase-authentication boundary.

Supabase's [session documentation](https://supabase.com/docs/guides/auth/sessions) says refresh sessions normally persist until terminated and hosted time-boxing, inactivity timeout and single-session settings require Pro or above. This minimum does not depend on those paid controls: it deliberately uses local fixed expiry. Supabase JWT expiry is still enforced when accepting the login proof; it does not silently become the expiry of the exchanged application session. Application-session revocation must affect D1 explicitly as described above.

## Identity mapping and authorization

Add nullable unique `users.supabase_sub` for one configured Supabase issuer/project. Verify provider JWT sub, then require its controlled mapping to an existing users.id. Before enabling new methods for either person, owner approves an exact Supabase-sub-to-existing-D1-ID manifest; verify subjects using actual successful provider authentication, not matching emails/usernames. Keep users.id, usernames, all ownership and learning FKs unchanged. Multiple historical accounts belonging to a person remain intact; map the selected account, leave others accessible through legacy login until a separate mapping/consolidation decision. A unique subject cannot map to multiple users. If another subject must share an account, stop for explicit policy/schema review rather than merge automatically.

Initially unmapped Supabase subjects get a generic not-enabled response: no automatic D1 user creation, ownership transfer or public signup provisioning. Supabase may create an Auth record during its flow, but that alone grants no Flashcards access. Google-first and OTP-first must converge on the approved subject. Concurrent mapping updates use unique constraints and expected-old-value predicates; an active session/client cannot choose or rewrite its mapping. Adding a mapping does not replace existing sessions or rename the user. Legacy username-upsert behavior stays operational, so accidental extra test usernames remain possible; report them, do not auto-merge them.

Supabase [identity linking](https://supabase.com/docs/guides/auth/auth-identity-linking) automatically links compatible identities sharing verified email. Test Google-first and OTP-first for the same verified mailbox resolve to the same sub and D1 user. Different mailboxes may yield distinct Supabase users: do not merge them in D1. No custom linking UI is required initially. No automatic link from Supabase email to historical D1 identities is allowed. Email changes remain a Supabase concern; no local recovery/claim subsystem.

Preserve decks.ts, permissions.ts, collaborators.ts and study authorization keyed by users.id. SHARED remains readable by authenticated users; ownership/editor rules remain as inventoried. No Supabase RLS replacement is needed for D1. Supabase holds its managed Auth records in its own PostgreSQL; no deck/card/progress data is moved there. Do not create public application tables in that project.

Management API continues accepting only fc_ bearer tokens via authenticateClient, checking digest, expiry, revocation, can_write and current deck permissions. Supabase JWTs and browser cookies do not become Management API tokens. Application-session revocation does not alter fc_ scope: incident handling must explicitly revoke API tokens if desired. Retain token hashes, identities, idempotency and revision semantics; no ownership, membership or token-identity changes are planned for parallel rollout.

## Authentication sequences

### Google

1. Same-origin POST Google start reserves a short-lived browser-bound transaction. Worker uses per-request Supabase client with PKCE, persistence/auto-refresh disabled; store verifier in short-lived HttpOnly Secure SameSite=Lax cookie. Fixed callback URL and allowlisted local return paths only.
2. Redirect top-level through Supabase to Google; Supabase handles Google provider state/nonce and callback. Google client secret stays in Supabase configuration, never the browser/Worker bundle. Request only openid/email/profile; no Google API access or offline scopes.
3. Worker callback checks matching local browser transaction and expiry, consumes it, exchanges the single-use Supabase code with verifier, validates returned access JWT and calls Supabase getUser with that access token to establish current user status. No D1 session from URL parameters alone. Clear verifier/transaction cookies on success/failure. Fail closed on mismatched/absent transaction, replay or provider denial.
4. Resolve sub to D1, issue fresh opaque cookie, discard access/refresh/provider tokens, return to fixed safe page and check /api/home. OAuth callback is a GET exception to browser POST Origin rules; browser binding/PKCE supplies login-CSRF protection. Ordinary state changes still require Origin/CSRF controls. Detailed cookie storage adapter and callback correlation must be validated against the pinned SDK in a spike; do not invent a hand-built OAuth protocol.

[Supabase Google guide](https://supabase.com/docs/guides/auth/social-sign-in/auth-google) documents provider setup and client flows. [Server-side guidance](https://supabase.com/docs/guides/auth/server-side/advanced-guide) explains PKCE and token handling. Configure exact site/redirect allowlists, Google consent screen/authorized domains and Supabase callback; never wildcard production redirects. Publish Google consent configuration appropriately before public access; test-mode users are not general production eligibility. Follow [Google OAuth production policies](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance).

### Email OTP on every device

Worker POST start calls Supabase signInWithOtp. Configure the Supabase template to display its token, because this API otherwise sends a magic link. POST verify calls verifyOtp with email/token and email type, validates Supabase identity as above and creates the same local session. Supabase generates, stores, expires and single-use verifies OTPs; Flashcards stores no OTP or MAC. Choose five-minute OTP expiry, 60-second resend cooldown and a short-lived browser context. New registrations follow the owner-approved signup policy. Generic acknowledgment/errors avoid exposing whether an email exists; never return upstream sensitive error details.

The [passwordless documentation](https://supabase.com/docs/guides/auth/auth-email-passwordless) specifies template token, automatic signup, default 60-second request interval and one-hour expiry. Reduce expiry in project configuration. Test replay, simultaneous verify and resend semantics against the selected Supabase version: do not assert configurable per-code attempt caps absent evidence. Supabase can create a session even if the Worker response is lost; require a fresh flow rather than caching refresh tokens for redelivery.

Layer D1 atomic budgets at the Worker: suggested start 3 sends/15 minutes/email, 10/day/email, 20/hour/IP with NAT accommodation; five verify submissions/browser context, plus IP and email verify budgets. These are application limits, not Supabase guarantees. Supabase public endpoints/publishable key can bypass the Worker: configure provider-side rate limits/CAPTCHA if needed, monitor mail quota and do not promise Worker counters enforce a global provider ceiling. Server-originated Auth requests may share egress IP limits; do not forward arbitrary caller IP headers or add a service-role key merely to bypass them. Verify effective limits in staging. Use keyed short-lived email/IP pseudonyms, never raw OTP logging.

[Supabase rate-limit documentation](https://supabase.com/docs/guides/auth/rate-limits) is authoritative for endpoint-specific defaults and 429 behavior; configure and record project values. Do not retry mail sends automatically on ambiguous timeout. Show cooldown/retry guidance; delayed mail never extends code validity. Basic server-rendered input remains available on TVs.

## JWT verification in Workers

Recommend `jose` remote JWKS verification at the direct-login boundary, not on every D1 API call. Select asymmetric signing keys in Supabase (prefer ES256); allow only the configured algorithm. Fixed issuer `https://<configured-project>/auth/v1` and JWKS `https://<configured-project>/auth/v1/.well-known/jwks.json`, never derived from untrusted JWT jku/iss. Check signature, issuer, audience authenticated, exp, nbf when present, sensible iat, nonempty UUID sub, role authenticated, and session_id for normal user sessions; reject anonymous, service-role, publishable API keys and wrong-project tokens. Use small bounded clock tolerance. Do not treat role as a Flashcards administrator role, and do not authorize from user_metadata.

Use a module-level remote key set with explicitly bounded cache (no more than 10 minutes), refresh on unknown kid with cooldown/rate limiting, and fail closed if no trustworthy key is available. Known cached keys can validate during brief network failure only within cache policy. Cache public keys only; never auth responses. Supabase edge also caches JWKS; planned rotation must allow overlap and emergency cache purge/restart. Existing exchanged local sessions require their own revocation during a key-compromise incident.

The [Supabase JWT guide](https://supabase.com/docs/guides/auth/jwts) documents JWKS, edge caching for ten minutes, rotation wait guidance of at least twenty minutes and jose. Use online getUser at login to check current provider user; local JWT verification alone does not check logout/ban. Legacy HS256 secrets do not have public verification keys; use getUser as fallback during setup, rather than copying the shared signing secret. No service_role secret is required in the normal Worker flow.

## Minimal QR delegation

1. TV POST start creates five-minute pending D1 request. Generate independent 256-bit poll and approval secrets with Workers Web Crypto, store hashes, and place poll secret in a temporary HttpOnly Secure cookie. Render QR containing first-party approval URL with approval secret in fragment, plus eight-character unambiguous base32 manual code. Store manual-code digest with UNIQUE index/collision retry. Short code never acts as polling secret.
2. Phone opens /activate, POSTs fragment secret (then clears history fragment) or manual code. Keep pending context through Google/OTP via browser-bound short-lived cookie. GET/scan never authorizes. No third-party analytics on these pages; no-referrer, no-store, no token logging.
3. Authenticated phone sees its account, untrusted device label, time and matching confirmation phrase visible on TV; explicitly POST approve or deny with CSRF protection. Any currently authenticated Flashcards phone session can approve, including legacy login; no separate authorization rule or Supabase-only requirement applies. Approval grants a fresh 30-day device session, so an authenticated session can deliberately extend access through delegation; this is explicit consent, not automatic renewal. Reject expired/revoked approver. Conditional pending-to-approved update binds exact users.id and approving session hash; competing account/denial/expiry cannot overwrite state. Explain forwarded-QR phishing risk; approve only a device the user initiated.
4. TV POST polls using its cookie every five seconds, jittered, no overlapping polls, stops after five minutes or terminal state. Pending response contains no identity/tokens. Approved poll consumes and issues TV's own new local cookie, valid for 30 days from completion. Phone token never crosses devices. Manual refresh fallback avoids dependence on background timers.
5. Transactional D1 batch first conditionally updates approved-to-consumed with unique redemption marker, poll hash, unexpired request, still-valid approving Flashcards session and unchanged bound user. Next INSERT auth_sessions SELECT is gated by that marker. Check affected rows before Set-Cookie. Only one concurrent poll wins. No unconditional session insert after a read. No cross-request BEGIN/COMMIT assumption; use [D1 batch semantics](https://developers.cloudflare.com/d1/worker-api/d1-database/). Reads/approval/redemption must use primary/consistent sessions if replicas are enabled.

Denied/expired/consumed rows cannot be revived. Lost winning response requires restart; no plaintext session is stored to redeliver. Page refresh can retain pending cookie until expiry; start-new invalidates prior request where known. Apply server poll cadence limit and start/manual lookup budgets (e.g. five starts/15min/IP, five lookup failures/15min/browser, twenty/IP), bounded TTL cleanup and no per-poll writes except bounded abuse buckets. Logout-all invalidates pending/approved grants; revoke-current blocks grants approved by that session. Completed TV sessions are independent; revoking the phone alone does not revoke an already issued TV session, but logout-all does.

No WebSockets, queues, Redis, Realtime, Durable Objects or general device framework. Direct OTP on TV stays available when scanning is inconvenient. LG cookie failures cannot be repaired by QR: retain cookie diagnostics but redact all auth material. Chrome79 build target is not proof of TV support. Use basic forms, image QR, large text/focus targets and top-level navigation; no client Supabase SDK is required on TV. [LG engine documentation](https://webostv.developer.lge.com/develop/specifications/web-api-and-web-engine) shows substantial version variation; test actual standalone browsers, TLS and persistence. Do not require Google UI on constrained TVs; QR/OTP are the reliable alternatives.

## Exact proposed D1 changes (design, not executed SQL)

| Object | Required definition/change |
|---|---|
| users | add nullable supabase_sub TEXT with unique index for non-null values; all existing columns/IDs unchanged. Null remains valid for legacy login/session validation. No new role or account-disable field required. |
| auth_sessions | **no column changes**: retain token_hash PK, user_id FK, expires_at and expiry index; add user_id index for logout-all. Existing positional three-column INSERT and old binary remain compatible. Shared issuance helper may be extracted without changing legacy semantics. No method metadata required for common authorization. |
| auth_device_requests (new) | id TEXT PK; poll_hash TEXT NOT NULL UNIQUE; approval_hash TEXT NOT NULL UNIQUE; manual_hash TEXT NOT NULL UNIQUE; state TEXT CHECK pending/approved/denied/consumed; created_at/expires_at INTEGER NOT NULL; nullable user_id FK users(id), approver_hash TEXT, redemption_marker TEXT UNIQUE. Pending has no user; approved requires user and approver. Index expires_at and user_id. approver_hash is a semantic session reference; redemption checks authoritative auth_sessions. New session expires 30 days after completion. |
| login_limits | reuse key/count/expires_at for namespaced send/verify/QR budgets; no new counter table. Do not clear token-operation budgets. |

No user_emails, custom OTP challenges, auth_claims, refresh-token vault, admin-role or Supabase application tables. PKCE/browser transaction state can use short-lived cookies and existing login_limits for replay markers; exchange single-use code and consume browser transaction once. Cookies contain only verifier/opaque context with bounded TTL and no remote data; validate integrity/binding before trusting any field. QR labels are optional presentation data, not identity. Reuse existing 72-character random cookie format and SHA-256 digest to minimize parser changes; UUID concatenation remains cryptographically random. Reuse Secure/HttpOnly/SameSite=Lax and no-store, rotate current cookie on login. No IP-binding of sessions.

## Services, libraries and current free limits

Official sources verified 2026-11-22. No accounts were created; effective account limits/approvals still require setup verification. Free hosted tiers are revocable service offers, distinct from open-source software licenses.

- Server-only `@supabase/supabase-js` (MIT) for supported Auth/PKCE calls with per-request storage and no global mutable session. `jose` (MIT, [Workers supported](https://github.com/panva/jose)) for claims/JWKS. `qrcode` (MIT, [server SVG support](https://github.com/soldair/node-qrcode)) for QR images; benchmark CPU. Web Crypto already provides random secrets and SHA-256; no OTP crypto library. No @supabase/ssr is required if SDK verifier storage is adapted narrowly in Worker cookies; confirm that adapter in the spike. Native fetch suffices, but hand-building all Auth exchanges saves little versus the SDK.
- [Supabase Free pricing](https://supabase.com/pricing): 50,000 MAU, two active projects, 500 MB managed database, 5 GB egress; social OAuth is included. Pauses after one week of inactivity; community support, no production availability guarantee. Not a time-limited trial. Google OAuth availability does not mean SAML/enterprise SSO is free. Auth-only usage still consumes managed database/egress. Public production use is possible under limits and policies, but continuous availability may require paid service. Do not defeat inactivity rules with artificial keepalive traffic.
- [Supabase SMTP](https://supabase.com/docs/guides/auth/auth-smtp): default sender only permits project-team addresses, two emails/hour, best effort; unsuitable for general OTP. Custom SMTP supports general recipients and initially has a 30-message/hour safeguard that must be adjusted. SMTP credentials live in Supabase, not Workers. Configure authenticated sender domain, SPF/DKIM/DMARC, disable tracking, monitor delivery/bounces and privacy. No Send Email hook/Edge Function is necessary.

Daily exhaustion causes failures; budgets include the existing application. Index lookup design and bounded cleanup matter. Profile cold SDK/JWKS imports, JWT verification and QR rendering against CPU limit; network wait is not CPU.

Illustrative active-user model, not measured: one direct login and one full five-minute QR attempt/day/user, 60 polls plus ten auth/control requests; allow 200 indexed rows read and 30 written/user/day including index/counter allowance. No per-poll session heartbeat. Add existing study/import traffic separately.

All are below Supabase MAU ceiling if distinct monthly population remains <=50k. Email is the bottleneck: 100/day exhausts Resend daily allowance without retries; 1,000/day exceeds both providers. Sparse two-person use risks Supabase inactivity pause despite low cost. Measure actual sizes; existing content/history may dominate. Alert on 70/85/95% quotas. A $0 recurring hosted configuration is plausible for current usage, not a guarantee of zero-cost growth or uptime.

## Parallel rollout, checkpoints and rollback

Phases 1-4 add identity mappings and login choices only. The previous bulk deck-transfer/cutover plan is superseded: no ownership transfer, new application users, learning-state consolidation, token rekeying or mass session invalidation is required. Retain all existing users and references inventoried in AUTH-INVENTORY.md. If later ownership cleanup is wanted, obtain a separate exact manifest, collision policy and data-change approval. Do not replay history INSERTs or delete users; both risk cascades/progress corruption.

1. Preparation: baseline legacy login/session expiry, deck/card/permission/history and Management API behavior; inventory actual selected-environment references only when authorized; approve verified sub-to-existing-ID mappings. Take full consistent restricted D1 backup, record app version and nonsecret config; restore/dry-run mappings on isolated copy. Gate: unchanged resources and mapping uniqueness. Rollback checkpoint: pre-mapping snapshot plus inverse mapping.
2. Supabase: separate flags for Google and Email OTP, legacy always available. Issue the same 30-day cookies only after validated mapped identity. Gate: both new methods and legacy converge on expected IDs; no added application users/ownership changes. Rollback: disable affected new method and revert compatible application build while retaining additive schema, legacy and existing cookies. Mapping removal prevents new Supabase login, not revocation of existing cookies: revoke those explicitly if necessary.
3. QR: independent flag, five-minute requests, explicit authenticated approval and atomic one-use session issue. Gate: fresh independent 30-day cookie, all-session revocation and replay races tested. Rollback: disable QR starts/decisions/polls and invalidate outstanding requests; retain other methods and established sessions unless specifically revoked. UI flag alone is insufficient; endpoints enforce it.
4. Validation: all methods, both people's data/access/history/API credentials, actual LG hardware and concurrency pass. Record evidence and owner review. Rollback: disable new paths selectively; repair mapping via approved inverse edits rather than restoring old data over new learning activity. Full restore only before writes resume or with separately approved reconciliation. Supabase/D1 changes are not cross-service atomic; never delete provider identities as rollback shortcut.
5. Legacy retirement: **separate proposal, explicit owner approval and separate change** after Phase 4. Inventory login form/API/ACCESS_CODE, tests, scripts, docs and devices still relying on it. Only then consider removing equalCode/shared-code upsert/form/config and obsolete login counters. No Phase 1-4 acceptance criterion requires removal. Retain users/auth_sessions/login_limits token budgets, api_tokens/api_creates, learning/content tables and migration history.

## Owner decisions still required

Exact verified provider-sub-to-existing-user mappings for both people, which historical account each person will use, provider/domain/free-plan operational readiness, actual LG support floor, backup/privacy retention and validation window. Initial public provisioning is disabled to avoid duplicates; expansion needs explicit policy approval. The approved 30-day duration, parallel legacy operation and common authorization are fixed requirements. Supabase revocation remains distinct from D1 session revocation and legacy re-login. Any future consolidation or legacy retirement requires its own approval; neither is automatically included in implementation.

## Implementation update (feature/auth)

Implementation is now authorized and present, superseding earlier analysis-only status text above. See [AUTH-SETUP.md](AUTH-SETUP.md) for exact bindings, Google/Supabase/SMTP setup, controlled mapping, backup, rollback and LG checklist. Migration 0012 adds the approved mapping/index/device table; auth_sessions remains three columns and its INSERT now names columns explicitly. No real mappings, remote migrations, deployment or data transfers were performed. New flags default off; legacy login/cookies/30-day lifetime remain.

Code: server/supabase-auth.ts validates provider identity and issues mapped local sessions; server/device-auth.ts uses atomic one-time delegation; auth.ts adds shared session issue and logout-all; api.ts enforces existing CSRF/request checks and primary D1 access. ui/AuthMethods.tsx and /activate provide theme-compatible login/approval UI. Authentication tests use mocked provider responses and real isolated D1; live provider/SMTP and real LG validation remain external gates. Phase 5 remains excluded.

Implementation details replacing earlier optional design choices: Google callback URL is fixed, with a single-use browser transaction and SDK PKCE binding instead of a variable state query redirect. The SDK uses ephemeral per-request storage (persistSession enables its PKCE adapter, not persistent refresh storage). QR context/preview/approve/deny are separate POST actions under /api/auth/device. Device label and independent confirmation phrase are presentation columns; no manual activation credential is stored plaintext. Email/IP budget identifiers use HMAC with AUTH_RATE_LIMIT_SECRET. Runtime invocation URL logging is disabled to protect callback codes. No per-method authorization or subject requirement is added to existing cookie validation.
